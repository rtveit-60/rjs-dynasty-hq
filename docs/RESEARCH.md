### Confirmed during milestone 1 (all verified in code)

- Binary refs are 32 bits: first 15 = tableId, last 17 = row. `Team.Roster` → array table of Player refs works as the roster join (85 players for the user's Duke team); `Team.DepthChart` → per-position slot refs → ordered Player refs (35 slots incl. situational: 3DRB, PWHB, SLCB, RLE/RRE/RDT, KOS, GAD).
- `Player.Weight` is stored as **pounds − 160** (Madden lineage) — always add 160.
- Team naming: `LongName` = school ("Duke"), `NickName` = mascot ("Blue Devils"), `DisplayName` similar to LongName. 143 named teams in the Team main table.
- Dev traits: `Normal`, `College_Impact`, `College_Star`, `College_Elite`. SchoolYear: Freshman…Senior; RedshirtStatus: `Eligible`, `Previous` (more values likely league-wide).
- `TEAM_BACKGROUNDCOLORR/G/B` (+`R2/G2/B2` secondary) are 0–255 team colors and match real branding (Duke `#1f3d7b`, Alabama `#b30839`).
- Parse cost: ~300ms initial load; re-scoping to another school from a cached parse ~7ms. Full refresh (hash+copy+parse+extract) comfortably under 2s.

### Coach table — schema drift, SOLVED (2026-08-27)

- The bundled C27_468_2 schema **contains** a `Coach` definition (137 attributes), but the save's Coach table header declares **138 members** — a title update added a field. madden-franchise's `set schema` silently refuses on any attribute-count mismatch and falls back to generic `Field_N` names, which also kills table2 string decoding (names).
- Field layout comes from the file's own offset table, paired to schema attributes **by index** — so the fix (implemented in `src/main/parser/coach-schema.ts`) inserts one pad attribute and scans insertion positions, scoring decoded records against plausibility oracles (readable names, sane ages, valid team indexes). Verified: user coach decodes fully (name, `IsUserControlled: true`, `Position: HeadCoach`), real coach names league-wide.
- **The missing member is identified (2026-09-02): `LeagueJobMotivation`** (enum `CFBHigh=0 CFBLow=1 Neutral=2 NFLLow=3 NFLHigh=4`, 3 bits), sitting at bundled index **128, between `IsNIL` and `Name`**. Three of the four `Coach` copies in the game's Core-Schemas XML have 137 attributes, the fourth 138, and the diff is exactly this field; with the pad there every one of the 138 file offsets has the width its type demands, on both save eras (2026 Virginia and 2034 Duke, same header: 138 members, record size 184). **The original scan had a silent bug**: it walked insertion points from the end and stopped at the first index whose *pre-pad* oracle fields decoded, which parked the pad at 137 — so every attribute past 128 was misassigned (`Name` unreadable, `YearsCoaching` read from `SpecialtyType`'s 2 bits, `SeasonStartJobSecurityStatus` from `PersuadeAttempts` — the old "reads undefined" note) while everything before 128 was correct. `ensureCoachSchema` now tries the known slot (the index of `Name`) first and requires a perfect oracle on **both** sides of the insertion (`Name` + `YearsCoaching` joined the oracle), falling back to the full scan only if that fails. Probe: scratch `pad-check` on both samples → pad 128, `YearsCoaching` 0–43, all five security statuses and three specialty types decode. **Never write Coach fields past the pad without this fix** — and with it the whole record is inside the safe window.

### Coach talent trees — FOUND (2026-09-02): topology, prerequisites, purchase machine

The tree definitions were half-found in the field-map dig; the missing half — the node graph — lives in a **second FTC store** in globals (chunk `8b318df6-b3ad-f195-4a0d-0efa29a0d3b8`, 492 KB inflated, 304 mostly-UI tables): `TemplateTalentSubTreeNode` (205 rows: `NodeIndex`, `Level`, `Column`, `EvaluationTemplate` AllParents/SingleParent/True/XOR, `ChildNodeList`) plus its child arrays. The plain chunk scanner never saw it because it does not inflate zlib payloads. The tuning store's `TemplateTalentSubTree.TemplateNodeList` arrays reference those rows by row number; four sibling copies of each store are byte-identical, so resolve by table name within whichever pair opens, never by hard-coded id.

- **Shapes**: only 5 of 13 template rows are used — 8×4 (33 nodes: archetype node + eight chains L1→L2→L3→L4) for Motivator / Tactician / Recruiter / Architect / Scheme Guru / Strategist / Elite Recruiter / Talent Developer and (a second 8×4) Master Motivator; 7×3 (22) Program Builder; 9×1 star (10) CEO; 4×1 star (5) Rainmaker and Visionary. Node 0 (eval `True`) is the gate; every other node has exactly one parent. **Verified against 2,392 live coach trees (5 saves)**: a node is `Purchasable` only under an `Owned` parent (0 exceptions) and `Owned` only under an `Owned` parent (one CPU coach anomaly the game tolerates).
- **Index conventions**: `TalentSubTreeStatus[i]` ↔ `StaticTalentTree.TalentSubTreeList[i]` (HC row 1 = 13 subtrees; OC and DC both row 0 = the first 11, row-for-row identical); `TalentStatusN` ↔ `OrderedTalentNodeList[N]` ↔ template `NodeIndex N`. `TalentStatus` NotOwned=0 Purchasable=1 Owned=2 Locked=3; slots past the node count stay 0; `Version` always 0.
- **Prerequisites** (`CoachTalentPrerequisiteGoal`, 13 rows; member order = inheritance order Goal → CoachGoal → CoachMilestoneGoal → CoachStatMilestoneGoal → own, confirmed by bit widths): base subtrees `MinCoachLevel` 10 (259/259 sub-level-10 coaches Locked); Architect 4 career rival wins; Master Motivator 5 players drafted; Elite Recruiter 2 top-5 classes; Scheme Guru 8 Top-25 wins; Strategist 4 bowl wins; Talent Developer 2 first-rounders; Program Builder 5 playoff wins + 300 points spent; CEO 2 national titles + 500 spent; Rainmaker = MVP+ membership flag; Visionary = created a coach in Madden 27. The 13-slot `TalentRequirements` int[] carries 200s on feeder archetypes — reported, not interpreted.
- **The purchase routine is native** (`TalentTreeEval.*`, `CoachProgressionEval.*` declared with GUIDs, no expression bodies; all 8,786 bodies grepped). Machine as observed: create-coach templates are all-zero except the backstory subtree's root `Owned`; a failed gate floods the whole subtree `Locked` (residue 3s below unowned parents appear only in the older dynasty; both 0 and 3 are game-valid there); buying flips the node to Owned and its direct children to Purchasable; `CoachPointsSpent` is a paid-points ledger (equals Σ owned cost in 75% of rows; discounts/refunds explain the rest — never recompute it); `Coach.CoachPoints` is the unspent balance (not derivable from level: the user HC holds 1,698 unspent + 7,695 spent). `DominantArchetype` always names a subtree whose root is Owned (2,136/2,136) but no formula over the statuses reproduces the choice (82% best fit) — stored state.
- **Editor recipe (shipped)**: per changed subtree the dialog sends the wanted owned set (owning a node owns its ancestors, releasing one releases its descendants); main rejects a set that isn't closed under parents, then rewrites the vector — owned → 2, parent-owned or root → 1, else 0 — and moves `CoachPointsSpent` by the cost delta (clamped 0–2000), leaving `CoachPoints` alone. An unowned root is written Purchasable (the game re-evaluates gates natively and may relock). Setting `DominantArchetype` requires that subtree's root to be Owned after the edit. A role change swaps `Position`/`PrevPosition` with the same staff's holder; a coordinator promoted to head coach gets slots 11–12 provisioned as locked, unspent rows (the template shape for a gated subtree) so the 13-slot HC tree reads cleanly. Open in-game: when `CoachTalentEffects` is rebuilt after an external tree edit (expect the next weekly advance), whether an app-set Purchasable root survives a genuinely unmet gate, and whether the swapped staff plays through a week.
- **Generated**: `node scripts/extract-coach-talents.ts` → `src/shared/coach-talents.ts` (13 subtrees, 339 nodes: name, description, cost, level/column, parent/children, branch title, prerequisite; `COACH_ARCHETYPE_NAMES` / `COACH_BACKSTORY_NAMES` from the enum display tables — value 1 shows "Tactician" for the save's `Schemer`). Anchors: subtree order, node counts 33×9/5/5/22/10, single-parent graph, CEO/Program Builder archetype values, level-10 and 500-point prerequisites, coordinator tree = HC slots 0–10.
- **The Coach table is the Tendencies/Playbook goldmine**: `COACH_OFFTENDENCYRUNPASS`, `COACH_DEFTENDENCYRUNPASS`, `COACH_OFFTENDENCYAGGRESSCONSERV`, `COACH_DEFTENDENCYAGGRESSCONSERV`, `COACH_RBTENDENCY`, `COACH_ADAPTIVE_AI`, `COACH_NO_HUDDLE_TEMPO`, `COACH_DEFENSETYPE`, `OffensivePlaybook`/`DefensivePlaybook` (refs), `OffensiveScheme`/`DefensiveScheme`, plus `CoachPrestige` (e.g. "Aplus"), `AlmaMater`, `HomeState`, contract fields, per-position ratings (`COACH_QB`…`COACH_S`), and `PrimaryPipeline`.
- **Coach↔Team join**: `Coach.TeamIndex` matches `Team.TeamIndex` (a field), NOT the Team table row. 255 = unemployed. `Position` enum: HeadCoach, OffensiveCoordinator, DefensiveCoordinator.
- **User detection**: `FranchiseUser` (table 4349) is schema'd; its `UserEntity` ref points at the user's Coach row. Simpler still: `Coach.IsUserControlled`. Both verified.

- **How the game generates AD goals** (from the FranTk schema/expression XML in the `9b964b0c…` globals chunk): a blocking `AssignSeasonGoalsTransaction` runs `CoachGoalsEval.AssignSeasonalGoals(team)` per team at season start (reactions exist for LeagueSetup / PreSeasonStart / SeasonStart, plus TU2 variants). Scoring: each goal's `ContractPointsPass/Fail` are scaled by priority-rank multipliers (`ADTuning.Pass/FailValueMultiplier*`) and by the AD's demeanor (`ADDemeanorTuning.Pass/FailValueMultiplier`, plus `ADDemeanorToJobDifficultyScore`); progress evaluates on `Pass/FailEvalFrequency` cadence (weekly/end-of-week/bowl-bid reactions), banks into `Coach.EarnedContractPoints_ThisYear` against `Team.ExpectedContractPoints_ThisYear`, and feeds job security. `ADDemeanorTuning` also holds the AD's flavor strings (`MessageHotSeat`, `MessageFire`, `MessageOffer`, `MessageRenew`, `Descriptor`) — same Tuning store as the goal wording, which **is readable after all**: see "AD goal wording — FOUND" below for where the stores physically live and how to open them. Each bundle is the same texture layout extract-game-icons decodes: 184-byte res header (format at 0x0C = 0x42 BC7, width/height at 0x16/0x18) + a pixel chunk — portraits are BC7 512×512 (256KB mip 0).

**The join key is `Player.GenericHeadAssetName`** ("Generic_0877_P_T0042_H_6_3", "Unique_SyPape_6133"), lowercased into the bundle name — for unique AND generic players alike. ⚠️ `PLYR_PORTRAIT` is NOT a reliable asset key: thousands of players whose GH says `Unique_<name>_<assetId>` carry a *different* PLYR_PORTRAIT (e.g. pid 11425 vs asset 6133); only ~8.6k of 16.3k pids happen to match a unique bundle id. PLYR_PORTRAIT is what the app's `portrait://<id>` protocol resolves, so extraction writes `<pid>.png` decoded from the GH-named bundle. `Player.PLYR_GENERICHEAD` ("6_H_BD_01" / "NoHead") is the 3D head recipe, unrelated to portraits.

**Coaches mirror players**: `Coach.GenericHeadAssetName` ("Unique_C_DiazManny_503" / "Generic_0010_C_T0106_T_6_1" — generated coaches incl. the user's created coach draw from a 186-bundle generic coach pool) names the `nilcp_` bundle; `Coach.Portrait` is the numeric id (same id≠asset drift: Diaz asset 503, id 626). Coach ids overlap player ids, so files are `c<id>.png` and the `portrait://` protocol accepts `c\d+`. ⚠️ The asset-name field truncates long names with a trailing `-` ("...DesormeauxMicha-_581") — recover by matching bundle stem + trailing id (2 of 493 coaches in the test save).

`scripts/extract-portraits.ts <save> <outDir> [--team <TeamIndex>] [--recruits] [--all] [--size <px>]` extracts per user (coaches always included) (default scope: the save's user-controlled team; EA's art never enters the repo — same policy as game icons). BC7→PNG currently via python3+Pillow (dev/power-user); an in-app importer needs a JS BC7 decoder. Verified end-to-end: 85/85 Virginia players extracted, served over `portrait://`, real headshots on the Roster tab.

### Player editing — PROVEN (2026-08-30): madden-franchise round-trip + in-game acceptance

The library reads AND writes: `record.Field = value` then `franchise.save(path)` re-packs. Proven against real saves, then **in-game**: a library-written save loaded fine (renamed player, jersey, 99 SPD all displayed), and the game **recalculated OVR on load** from the edited ratings (stored 76 + speed 78→99 displayed as 82) — so the app never writes `OverallRating`; it lags in the app until the game's next save writes the recomputed value back.

- **Fidelity**: a zero-edit load→save round trip produces byte-identical *unpacked* content (31.1MB, same SHA-1); only the packed bytes differ (different compressor). Load ~250ms, save ~250ms.
- **Write traps** (all guarded in `src/main/editor.ts`): ints past the field's bit width **silently wrap** (200 into 7-bit StrengthRating reads back 72 — clamp 0–99 before writing); strings **silently truncate** at the schema cap (FirstName 17, LastName 21); enum fields accept **member-name strings only** (`rec.MentalAbility1 = 'Captain'` works, `= 5` throws), invalid names throw cleanly.
- **Field map**: names/jersey/56 `*Rating` ints all raw on the Player row. Mental abilities = `MentalAbility1..3` (`MentalAbilities` enum, identity) + `MentalAbilityRank1..3` (`AbilitiesRank`). Physical abilities = `PhysicalAbility1..5`, **tier only** — identity is fixed by `PlayerType` (see PHYSICAL_ABILITY_SLOTS). Recruits are the same Player-row write via `Recruit.Player` (key on the *player* row).
- **Write policy**: the app never writes the user's file. Edits land in a sibling save `<name>_RJsEdited` (game lists it — keeps the `DYNASTY-` prefix); an already-edited save updates in place after a timestamped backup in `userData/backups` (10 kept per name). Compare-and-swap guard: the source file's hash must still match the parse that's being edited, else the edit aborts and the pipeline refreshes. After a write the dashboard switches to follow the edited file; that one refresh suppresses media events (the diff keys roster moves by name — a rename would read as a fake departure+arrival).
- **Rename side effect**: commentary speaks the old surname — pronunciation keys off `Recruit.SurnameAudioID` / audio assets, not the string.
- Regression harness: `node scripts/edit-check.ts` (28 checks: form truth, sibling write with source bytes unchanged, in-place re-edit with backup, whole-payload rejection).

### Appearance & equipment — FOUND (2026-08-30): CharacterVisuals JSON blobs

Per-player appearance lives in **`CharacterVisuals`** (table 4231, capacity 17,000): each row's `RawData` is a **JSON blob** — `{ loadouts: [{ loadoutType, loadoutCategory, loadoutElements: [{ slotType, itemAssetName }] }], skinTone, bodyType }` (plus an `Overflow` ref field, zero in practice). **43 gear slot types** observed (FaceMask, Visor, MouthWear, FacePaint, hand/shoe/arm pairs, Towel, BackPlate, FlakJacket, tattoos, spats…), with per-slot vocabularies aggregated straight from dressed players (facemasks ×34, shoes ×98, gloves ×89 in the Virginia save). `skinTone` observed 1–8.

Facial-feature morphs do NOT exist in the save — they're baked into the head choice. Editable by picking among heads (pair the enum with an observed asset-name from a real player, never invent the string); portrait previews via the extraction pipeline's GenericHeadAssetName join are the path to a usable face picker.

### Gear vocabulary — FOUND (2026-08-30): the game's loadout JSONs, not the save

A save only shows the gear its players happen to wear (10 helmets, 34 facemasks in the Duke autosave). ### Created-recruit visibility — SOLVED (2026-08-30 night): slots, not rows

The game's prospect list walks an index built at class generation — **appended Recruit rows never join it**, no matter how real their fields look. Proven the hard way on a live dynasty: a created recruit was made field-for-field indistinguishable from a 104-recruit cohort (end-of-class NationalRank/PositionRank/StateRank, a full 10-school race from the spare pool, the NoHead head-enum convention) and stayed invisible through four in-game loads. Occupying an existing slot made him appear instantly.

- **The design**: a create TAKES OVER the class's lowest-ranked uncommitted filler at ≤3 stars — repoint the host Recruit row's `Player` ref at the new player, retire the displaced filler's player row, keep the slot's national rank/race/stage/offers, re-rank Position/StateRank at the end of the new pools. The ≤3★ gate keeps consecutive creates from cannibalizing earlier (4–5★) creations.
- **Recruit face convention**: class recruits pair the head ASSET with `PLYR_GENERICHEAD = NoHead` (252 of 253 QB recruits; 1 MorphHead). Face writes on recruits/creates keep NoHead; rostered players carry the catalog triple as observed.
- The class ships with exactly one hidden dud recruit (rank 0, zero-ref race) — the earlier "zero-ref race precedent" was the one invisible row in the file; never model creates on it.
- **Race plumbing** (for reference): `Recruit.TopSchoolsList` → `ProspectTargetSchool[]` row (always arraySize 10) → 10 `ProspectTargetSchool {TeamId, TeamInfluence}` elements. Element table is sized exactly for the class (41,010 = 4,101×10; 10 spare) and carries ~700 orphaned-but-unreachable rows the game tolerates — **never call `recalculateEmptyRecordReferences()` on it** (the library flags the pre-existing orphans and refuses the header update). `RecruitTarget` (4,870 rows) is the CPU schools' board entries (multi-row per recruit), not a class list; the save's `City` tables are empty shells.
- Load-failure red herrings from the same session: a heavily-rewritten save path can fail to load (blank UI/error) while byte-identical content loads under a fresh name — suspect game-session caching, duplicate copies of the same dynasty in the folder, or OneDrive churn before suspecting content; test with a fresh caps-and-hyphens filename and a full game restart.

### Face catalog — FOUND (2026-08-30): the asset name is the whole identity

`GenericHeadAssetName` splits into two families. **`Unique_<Name>_<id>`** (10,932 players in the autosave) is an individual person's scanned face + portrait — never offered for created recruits. **`Generic_<portrait>_P_<Txxxx>_<cat>_<tone>_<n>`** (3,998 distinct assets across 5,323 wearers) is the shareable art pool, and the name itself encodes everything the picker needs:

- **Segment 1 = the portrait id** (`Generic_0877_…` → `PLYR_PORTRAIT` 877). Observed `PLYR_PORTRAIT` agrees on every distinct generic asset in every sample checked (one autosave had a single mis-tagged wearer; requiring agreement drops it).
- **Penultimate segment = the native skin tone (1–8)**. Matches the wearers' visuals-blob `skinTone` on 392 of 398 dressed wearers (the six are custom-painted individuals) — and unlike visuals-derived tones it covers the whole pool, since **most generic-headed players carry no visuals row at all**.
- **`PLYR_GENERICHEAD` is usually `NoHead`** on generic wearers (2,216 of 2,860 in the Virginia save) — the enum is optional; the game renders from the asset name alone. The catalog carries whichever enum value the first observed wearer had, `NoHead` included. The visuals JSON holds only `loadouts` + `skinTone` — no head reference — so a cloned base loadout can't smuggle in a different face.
- The skin-tone scale is **1–8** (719 tone-8 generic assets exist); an earlier 1–7 validation cap was wrong.
- `faceCatalog()` in `src/main/editor.ts` builds the pool per save (observed triples only, never invented); `buildCreateForm` flags which portrait ids exist in the user's portrait pack (`hasShot`, same lookup the `portrait://` protocol makes) so the picker sorts real headshots first. Chosen face writes `PLYR_GENERICHEAD` + `GenericHeadAssetName` + `PLYR_PORTRAIT` together and the UI aligns the visuals `skinTone` with the head's native tone.

### Weekly recruiting action hours — FOUND (2026-08-31): fixed prices, not freeform

Hours are not a number you choose: each weekly action has a fixed price and a prospect's week is the sum of selections. The definitions live in the franchise-common tuning store: **`RecruitingActionInfo`** (Field_0 = RecruitingActionType value, Field_4 = intensity value / 4 = none, **Field_2 = the hour cost**) joined through `RecruitingActionTypeEnumTableEntry` / `RecruitingActionIntensityEnumTableEntry` (Field_3 = value; three string-offset columns — recover each separately and keep the topically coherent one; merged/partial recoveries read neighboring pools as garbage).

- **The prices**: Contact Friends and Family 25 · DM the Player 10 · Search Social Media 5 · Send the House 50 · Schedule Visit 40 · Scouting 10 · Offer Scholarship 5 · Pitch: Soft Sell 20 / Hard Sell 40 / Sway 30. (`scripts/extract-recruiting-actions.ts` → `src/shared/recruiting-actions.ts`; anchors on Social 5 / House 50 / Hard 40 / Soft 20 / Sway 30.)
- **Identifier drift again**: the save's `ContactHighSchoolCoaches` checkbox field corresponds to NO action of that name — by five-way elimination over the ten action types it is the game's **"DM the Player"** (10 hrs). The UI shows the game's name.
- `RecruitingActionFeedbackEntry` rows (save) are the processed-week receipts per action (`HoursSpent`, influence gained, intel unlocked) — observed corroboration for the prices.
- **Per-prospect hours available — FOUND (2026-08-31)**: base + position-group perk bonus, both game-sourced.
  - **The base is flat tuning**: `RecruitingTunables` (single-row generic-schema tuning table, 88 members) read with the **Core-Schemas key** — the raw globals chunk `9b964b0c…` (20.8MB, `<FranTkData fileName="Core-Schemas"`) is the complete FranTk schema XML, and a generic tuning table's `Field_N` **is the XML attribute `idx="N"`**, so every member is nameable. `MaxTotalHoursOnRecruitPerWeek = 50` (Field_34); neighbors worth having: `MaxTimesScouted = 5` (33), `MaxRecruitingBoardTargets = 35` (29), `MaxTeamScholarshipOffers = 35` (32), `MaxRecruitVisitsPerWeek = 4` (31). - **Scouting is metered, not one-shot**: `MaxTimesScouted = 5` with per-pass unlock schedules (`ScoutingAttributesUnlockPercentage` = int[10] of 10s, `ScoutingPhysicalAbilityUnlockPercentage` = int[5] of 20s — five passes to full). ### Firing CPU coaches — VERDICT IN (2026-08-31): the hot seat is the input, PendingFire is inert

`Coach.ContractStatus` (decodable index range, inside the drift-safe window) is an enum whose members are the carousel's own state machine: `Signed=0, Expiring=1, PendingFire=2, PendingNFL=3, PendingRenewal=4, PendingRetire=5, PendingHire=6, FreeAgent=7, Retired=8, Deleted=9, None=10` — with range-marker aliases sharing values (`First_Active=0`, `First_Pending=2`, `Last_Active=5`, `Last_Pending=6`), so **reads must normalize by value** (the lib returns whichever name comes first: a PendingFire coach reads back `First_Pending`). Mid-season distribution in the sample: 429 active, 68 FreeAgent (the hiring pool), 1 Deleted, zero Pending states — consistent with the carousel setting them at season's end. `JobOpening.reason` includes `Fired`, the downstream state.

- **Write proven**: `rec.ContractStatus = 'PendingFire'` round-trips (value 2 persists; the read-back name is the alias). Undo = `'Signed'`.
- **IN-GAME VERDICT (2026-08-31, RJ simmed a full season to the carousel)**: an externally set PendingFire on a Safe coach **survives every weekly evaluation AND the offseason carousel untouched — and produces no firing**. It is the carousel's own output bookkeeping, not an input. The real input is the hot-seat system: **all 41 coaches the carousel fired entered the offseason as `Signed` + `CurrentJobSecurityStatus = HotSeat`** (their JobOpening rows carry `Reason = Fired`; season's 180 openings split Fired 41 / ContractEnding 129 / Pro 5 / NewJob 5). Security bands in a live dynasty: HotSeat 8–49%, Low 50–64, SafeForNow 62–79, Safe 71–100 (`CurrentJobSecurityPercentage`).
- **The shipped mechanism**: firing writes `CurrentJobSecurityStatus = 'HotSeat'` + `CurrentJobSecurityPercentage` at the save's own observed HotSeat minimum, and keeps PendingFire as the app's visible marker/undo handle (harmless — proven inert). Undo restores Signed + Safe at the observed Safe median. Caveat the dialog states: the AD re-evaluates security across played weeks, so a winning coach can climb off the seat — marking closest to season's end is most reliable; whether a mid-season HotSeat sticks through simmed weeks on a successful team is the remaining watch item.
- Never fire user-controlled coaches (guarded in `applyCoachFire`), and never write Coach fields past the drift-safe index window (~126) — the padded schema misdecodes there and a write would corrupt (see the Coach drift section).

### Player skill groups & caps — FOUND (2026-09-02): six per-archetype levels, 0–20

The game's Upgrade Player screen works on **skill groups**, and the save keeps exactly what the editor needs: `Player.SkillGroupCap1..6` (5-bit ints, **levels 0–20**, `PlayerProgressionTuning.SkillGroupCapMax = 20` — not OVR-style 0–99), `Player.SkillPoints` (15-bit, the unspent balance; recruits 0, nine-season seniors up to ~124) and `Player.ExperiencePoints` (the XP that converts to points via `PlayerSPThresholdSpline`, OVR 50..99 → 1,500..2,500 XP per point). Every real player carries all six caps (16,256 of 16,257 rows; the one blank is a TeamIndex-255 ghost). Caps are ceilings, not progress: they don't drift with school year, and they ladder by dev trait (Duke save, mean of six / share at 20: Normal 13.4 / 2.6% · Impact 15.3 / 12.5% · Star 17.1 / 28.8% · Elite 18.7 / 50%; recruits generate on the same ladder via `SkillGroupCapUpgradeGenerationInfo` {Normal 0/0, Impact 1/1, Star 2/1, Elite 3/2}).

- **Which group a slot IS depends on the ARCHETYPE**, not the position — from the franchise-common tuning store's `PlayerSkillGroup` rows (75; `Archetype: PlayerType`, `Name`, `PlayerSkillsBucket: PlayerSkillGroupBucket[]`, slot k ↔ `SkillGroupCap{k+1}`) → `PlayerSkillGroupBucket` (471: `Name`, `Primary/Secondary/TertiarySkills: PlayerSkill[]`, `DisplayInTopAttributes`, `GroupColorR/G/B`, `SPCost`/`MaxPotentialCost` splines) → `PlayerSkill` (54: `Name`, `Description`, `PlayerAbility` enum whose member names the save rating: `ManCoverage` → `ManCoverageRating`). C / G / OT order their groups differently, S_Zone differs from the other safeties, KP_Power swaps pairs with KP_Accurate, and same-named buckets carry archetype-specific skill lists (CB_Zone's "Man Coverage" primaries ≠ CB_MantoMan's). Rows whose `Archetype` is 0 and `Name` empty are position-level fallbacks (the `PositionToSkillGroup` table, 6–8 buckets incl. a hidden "Health") — not cap groups; the true QB_FieldGeneral row is the one wearing the game's label. The group `Name` strings equal `ARCHETYPE_LABELS` for the drifted ids ("Signal Caller" for OLB_PowerRusher), independently confirming that mapping.
- **Slot order verified against the save, not just read**: per archetype, the residualized correlation of `SkillGroupCap_k` with bucket j's mean primary rating picks j = k in 271/348 cases on the nine-season Duke save (chance 1/6; off-diagonals flat) — weaker on the freshly generated Virginia save (119/324) because caps only bite after seasons of progression.
- Level→rating splines exist (`HighestLevelSpline` 61…99, `HighLevelSpline` 56…99, `MediumLevelSpline` 55…89, `LowLevelSpline` 45…79, X = level 1..20) with weights Primary/Secondary/Tertiary 15/3/1 and adjustments 0/10/20; per-attribute **Cap Breakers** (`MaxAttributeCapBreakers` 5, `MaxCareerCapBreakers` 25) can push "any attribute beyond its current max cap" per the game's own perk text. No per-group current-level field exists on Player; the game recomputes level from ratings.
- **Spending points is NOT reconstructable from data (VERDICT, 2026-09-02)**: `PlayerProgressionEval_SpendSkillPoint` is declared in Core-Schemas (signature only: `player`, `playerType` → bool) but its body ships nowhere as text — a full 98,933-chunk sweep for `SpendSkillPoint|SkillGroupCap1|AbilityUpgradeCapPerSkillPoint|PlayerSPThresholdSpline` hits only the schema copies and type-name directories; the same holds for `IncreaseExperiencePoints`, `AutoProgressTeam`, `HandlePlayerAdvanceSchoolYear` and `Spline_CalculateY`. The spend logic is compiled into the executable. What the saves show empirically (save-to-save diffs, `sp-diff*.ts` in the 2026-09-02 scratchpad): a spend adds a flat **+2 to every rating in the bucket** (primary, secondary and tertiary alike; 15/3/1 weights and 0/10/20 adjustments never appear in increments), caps never move on a spend, cost is modally 1 point but could not be isolated (points also arrive from goals/awards/coach talents mid-window), and **no current-level field exists** — the best-fit level model (High spline over the 15/3/1 weighted mean with +10/+20 role adjustments) keeps level ≤ cap for only 97.3% of pairs, so it is an estimate, not the game's number. Confirmed for real: `ExperiencePoints` wraps at `PlayerSPThresholdSpline(OVR)` (5,366/5,366 XP drops consistent), so `SkillPoints` and XP are independent counters and editing `SkillPoints` directly is safe; incrementing a `SkillGroupCapN` is exactly what the game's own cap upgrades do (273 in-season cap changes observed, all +1, no side counter — the `MaxAttributeCapBreakers` counters live on Road-to-Glory's `NarrativePlayer`, not dynasty players). Per the never-guess rule the editor does not ship a "spend" action; the one experiment that settles it is RJ spending exactly 1 point on one known player's group in-game and saving, then `sp-diff.ts <before> <after>`.
- **Generated**: `node scripts/extract-skill-groups.ts [save]` → `src/shared/skill-groups.ts` (60 worn archetypes; the enum's unused Madden-lineage members — long snappers, returners, `GAD_Gadget`, `QB_StrongArm`, `WR_Slot`, `OLB_SpeedRusher` — have no rows and no players). Enum maps come from the Core-Schemas XML chunk, names from the store's string pools (bases anchored on known labels; the group pool's first row is an empty string, so its base sits on a NUL), every skill's rating field is proven to exist in the save's Player schema, and anchors assert the CB / KP_Power orders and `SkillGroupCapMax = 20`. The player editor's Skill Caps tab edits the six caps (0–20) and `SkillPoints` through the usual `_RJsEdited` path.

### Manual transfers — FOUND (2026-09-02): the game's own sign-player choreography

Team membership lives in exactly two structures, both of which a transfer must update (reverse-reference sweep of all 2,447 tables for one team's 85 players, 2034 save): `Player.TeamIndex` (matches `Team.TeamIndex`, not the row; 255 = none) and `Team.Roster` → a `Player[]` array table (152 records × 100 slots, `arraySize` = roster count; 133/138 teams agree exactly with the TeamIndex count, 0 mismatches). The only other live holder of a rostered player is the depth chart (`Team.DepthChart` → 35 per-position `Player[]` windows). `Team.ActiveRosterSize` is the game's cached counter (drifts: five teams read 86–87 against 85 real, all with `IRRemovalCount=1`) — adjusted, never trusted. `Team.CommittedPlayers` is the signing class (empty mid-season). Not constraints: jersey uniqueness (19 duplicates on one roster), `MarketedPlayers`/`FocusTrainingList`/`PracticeSquad`/`TradePlayerBlackList` (all empty), `TEAM_TYPE` on players (always Current), captains (`PLYR_ISCAPTAIN` — the game re-picks). Roster arrays are insertion-ordered (0/138 sorted by anything), transfers-in at the tail, so append is the right add.

**The procedure is the game's, read from Core-Schemas' expression bodies** — `TeamManager_SignPlayer`: `RemovePlayer(oldTeam)` (= `Roster.FindAndErase`, `ActiveRosterSize -= 1`; it does not touch the depth chart) then `AddPlayer(team, Signed)` (`PLYR_CONSECYEARSWITHTEAM = 0`, `Roster.Append`, `IsInjuredReserve = false`, `ActiveRosterSize += 1`) then `PlayerManager_UpdatePlayerContractStatus` (`PrevTeamIndex = oldTeam.TeamIndex`, `TeamIndex = newTeam.TeamIndex`); `StoryArcUtil_HasPlayerTransferred` is literally `TeamIndex != PrevTeamIndex`. Observed in the portal-window save (1,074 `Transfer_*` recruits): every portal player sits at `TeamIndex 255` with `PrevTeamIndex` = the old school, in no `Roster` array, keeping jersey/redshirt/NIL/visuals/stats; enrollment (the roster append) happens at a later offseason stage. Limits from the game: `RosterInfo.MaxRosterSize` (raw 32 above the schema's 53 floor = **85**, also `RegularSeason/OffSeason/EndOfWeekMaxRosterSize`), `OpenRosterSlotsForTeams = MaxRosterSize − ActiveRosterSize`, `LeagueSetting.MaxTransfersPerTeam = 8` (portal generation; not a roster invariant — Duke carries 10 transfers), `MinRosterSize 46`, `PlayerMovementLimit UNLIMITED`.

**Shipped** (`src/main/transfers.ts`, "Manual Transfers" on the Transfer Portal board): per move, remove from the old `Roster` (order-preserving compaction) and every old depth window, append to the new `Roster`, write `PrevTeamIndex`/`TeamIndex`/`PLYR_CONSECYEARSWITHTEAM = 0`/`IsInjuredReserve = false`, adjust both `ActiveRosterSize`s; rostered players only (recruit rows refused), `TEAM_TYPE = Current` teams only, resulting sizes ≤ the save's cap; verified on a cold reload (team index, previous team, both roster lists, no stale old-team window). The new team's depth windows are left for the game to refill (19/85 unwindowed players is normal; every window is full again in the later save). Team Needs recompute on the post-write refresh (`buildTeamNeeds` scans Player rows by TeamIndex; nothing is cached). Open in-game: whether a load alone refills the new team's windows for an app-added player; how the current-season stat row (tagged with the old `YEARBYYEARTEAMINDEX`) attributes after the move; whether an in-season over-cap roster would trigger the cut-day flow (the app refuses over-cap writes, so untested by design).

### Dynasty identity — FOUND (2026-09-01): FranchiseUser.TrophyProfileId is minted once per dynasty

The app's persisted stores (media state/feed, banked season history, the schedule bank) need a key that tells two *dynasties* apart, not just two schools — team row alone let a second dynasty sharing a school inherit the first one's feed and history, and the schedule bank had no key at all. The save carries exactly one field that fits:

- **`FranchiseUser.TrophyProfileId`** (string of ~15 digits, on the owner row — `AdminLevel = 'Owner'`; the table holds up to 32 users, solo dynasties have one). It is **minted at dynasty creation and never changes**: identical across save snapshots three seasons apart, across the user changing jobs mid-dynasty, across file renames, and across the app's `_RJsEdited` sibling writes.
- The value **decodes as a creation-moment timestamp in microseconds** (epoch ≈ 2005): deltas between this machine's dynasties reproduce their real creation dates (Jul 16 / Aug 2 / Aug ~5 / Aug 18 / Aug 29) to the day. Microsecond resolution makes cross-dynasty collision a non-issue.
- Verified across **seven lineages / ten files** (`node scripts/dynasty-id-probe.ts`): two DUKETOND snapshots agree; the Virginia family (midseason, two AUG29 autosaves, EDITED, EDITED_RJsEdited, EDIT-TEST, the forged MULTIUSER fixture) all agree; Pitt/Tennessee/Texas/JUL16 lineages all differ from them and each other. The one shared value (Pitt = AUG02 = TEXASMODSAVE) is real sharing: save-as forks of one created dynasty, which *should* share app state — they are one timeline.
- Not account-level: two dynasties made by the same EA profile on the same machine differ.

Shipped keying (2026-09-01): `Snapshot.dynastyId` (extract.ts) + `src/main/state-dirs.ts` — each store keeps a `d<id>` subfolder per dynasty (`media/d…/state-<row>.json`, `history/d…/seasons-<row>.json`, `schedules/d…/year-<year>.json`); a save with no readable id keeps the legacy flat layout. Migration is adopt-on-first-claim: row-keyed files move into the first dynasty that asks for that row; the schedule bank (no row key) moves wholesale to the first dynasty parsed. Adoption also prunes what it can prove foreign: banked years/events *later than the adopting save's current season* can't be that dynasty's (drops the phantom '30–'34 Virginia rows a Duke-era scoped parse had banked), a mid-regular-season adopt can't own a current-year bowl, and future-year schedule files are deleted outright (their own dynasty re-banks the season live on its next parse, verified). Same-year residue from a foreign dynasty is indistinguishable and rides along — accepted, matches pre-fix behavior exactly once.

### Player/coach/school stat history — FOUND (profiles, 2026-08-28)

Everything the profile pop-ups show (`src/main/parser/profile.ts`, checked by `scripts/profile-check.ts`):

## Game asset containers — Playbooks (SOLVED 2026-08-27)

Playbook contents are **not** in the save (confirmed earlier), but they extract cleanly from the game
install's Frostbite archives, fully offline. Full read path implemented in `scripts/fb/frostbite.ts`
(dev/build-time tooling) and productionized for runtime under `src/main/playbooks/`.

### Container format (this title = Manifest2019 Frostbite, FB version ~2021)

- `Data/layout.toc` — legacy Frostbite **DbObject** (varint-LEB128 typed tree). Signature header is the
  standard `00 D1 CE 01` + 0x22C bytes; **payload is plain** (no XOR/obfuscation on this branch — the
  BlockStream deobfuscator returns the raw payload for version byte 0x01). Carries `superBundles[]`
  (44 of them) and `installManifest.installChunks[]` (persistentIndex → cas directory).
- Superbundle `.toc` (e.g. `Data/Win32/playbooks.toc`, 500 bundles) — Manifest2019 layout: header of
  big-endian u32 offsets/counts, then a **huffman-coded bundle-name** table (flag bit `0x4`), a bundle
  record list, and an optional chunk list. Ported from Frosty 2.0 `Manifest2019AssetLoader.cs`.
- Bundle records: loadFlag 1 = record inline in the `.toc`. Bundle **meta** (asset name lists) is either
  inline or stored raw in a cas file (first location entry points at it) — playbook gamesheet bundles use
  the cas-stored-meta path. Meta = the standard `BinaryBundle` (salt "pecn", magic `0xED1CEDB8`).
- CAS file identifiers: location flags `0x01` (u32) and `0x80` (u32 pair) per Frosty, **plus `0x84`**
  (u64 identifier: isPatch bit 48, installChunkIndex = uint32 persistentIndex in bits 16-47, casIndex in
  bits 0-15) — new to this title; Frosty master doesn't emit it. Install-chunk persistentIndex keys are
  hash-valued uint32s, so `layout.toc` keys and location indices are normalized with `>>> 0`.
- CAS block stream: `u64 BE` header = flags(8) | decompressedSize(24) | compressionType(8) | `0x7`(4) |
  bufferSize(20). Compression types seen: **Oodle Kraken (`0x11`)** for real payloads. Decompressed via
  the game's own `oo2core_9_win64.dll` at the install root, called through the **koffi** FFI package
  (`OodleLZ_Decompress`, fuzzSafe=1, threadPhase=3). zlib(`0x02`)/zstd(`0x0f`)/none(`0x00`) also handled.
- **Type descriptors are locked**: EBX field layouts live in `SharedTypeDescriptors.ebx` inside
  `initfs_Win32`, which is **AES-encrypted** (title-specific InitFsKey; no plaintext). So generic RIFF-EBX
  field decoding is not available offline. Fortunately it isn't needed (below).

### Playbook data — the master gamesheet is self-describing protobuf (the win)

Each playbook lives in `Win32/playbooks.toc` bundle `.../gamesheets/college_<slug>_offense|defense_playbooks_brt`.
That bundle holds three EBX assets; the big one, `.../gamesheets/college_<slug>_<side>` (300–760 KB), embeds
the entire book as a **base64 CString → protobuf** blob (no type info required — protobuf is self-describing).
Decoder + model in `scripts/fb/playbook.ts` / `src/main/playbooks/`. Schema (field numbers verified against
Air Raid offense + Multiple defense, both offense & defense identical):

- root `1` → repeated: `1` = formation-family header `{1:name "Shotgun"/"4-3", 2:id, 3:type}`, and `2` =
  formation-with-plays `{ 1: Formation, 2..: Play[] }`.
- **Formation** `{1:name "Split Y-Flex", 2:id, 3/4:flags, 12: personnel package[], 13: alignment[]}`.
  - field `12` = personnel packages `{1:name "WR Swap"/"Dual TE"/…, 3: per-slot substitution refs}`.
  - field `13` = **alignment variants keyed by motion** `{1:name "Normal"/"M1left"…"M5right", 4: player[×11]}`.
    Each player `4` = `{ 1:{1:x, 2:y}, 2:{mirror x,y}, 3/4: facing° (90 = straight upfield), 5: slot/pos id,
    6: side, 7: position-type, 8: z-order, 13: index }`. **x,y are yards; LOS at y=0; +x right, −y behind LOS.**
- **Play** `{1:name "Y Cross"/"Mesh"…, 2:hash id, 3:sort, 5:personnel idx, 9/10:…, 24: receiver icons,
  28: assignment[×11]}`.
  - field `28` = per-player route assignment `{1:route-lib id, 2:?, 3: step[]}`. Each step `3` =
    `{1:stepType, <one of>: geometry}`; geometry sub-msg carries `{1:distance, 2:angle°, 3:speed% (100),
    5:0}` (a `run<angle>for<dist>` segment — matches the standalone `runroute/wr_run90for08…` asset names
    and their EBX float arrays). Assignment i ↔ alignment player i (both ×11).
  - field `24` = **controller passing-icon assignment** (offense only; absent on defense). One entry per
    eligible receiver, in the game's read order; each entry's field-1 is the receiver's **player index**
    (a permutation of the ~5 receiver slots). It is formation-level (identical across a formation's plays).
    The app maps read order → Xbox buttons: non-back receivers take the face buttons **X, Y, A, B**, backs
    the bumpers **RB, LB** — verified against the reference (Gun Bunch: P3=X, P5=Y, P4=A, P2=B, back P1=RB).
  - **Motion** is not per-play: it's a formation capability (the field-13 alignment variants M1left…M5right
    are the motioned alignments), chosen interactively in-game, so play art shows the base "Normal" set.
    Defensive coverage type (man/zone) isn't decoded; the app approximates zones from where each non-rushing
    defender's assignment ends.

### Which book a team runs — coach ref, not the scheme default (SOLVED 2026-08-27)

Three save fields describe a team's playbook; only one is the actual selection:

- **`Coach.OffensivePlaybook` / `DefensivePlaybook`** (on the head-coach record) — **authoritative**.
  32-bit binary refs (`refFromBinary`): top 15 bits = a game asset-table id (16456), **low 17 bits =
  the playbook row that identifies the book** (`decodePlaybookRow`). This is what a user coach's in-game
  selection updates, and it can differ from the team's default — verified: the user's Notre Dame HC and
  Ohio State's HC share offense row **89340**, so the user runs the Ohio State book, exactly as reported.
- `Team.TEAM_OFFPLAYBOOK` / `TEAM_DEFPLAYBOOK` — the team's **canonical default** (dense int enum:
  offense 200-401 alphabetical by team-book slug, defense 500-508 the nine base scheme books). Handy for
  building the row→slug map but *not* the live selection — Notre Dame's default is 326 = `washington_state`.
- `DefaultOffensiveScheme` / `DefaultDefensiveScheme` — scheme **archetype** enums (OFF_AIR_RAID,
  DEF_MULTIPLE_DEFENSE, …). Scheme family only; the fallback when the exact book isn't bundled.

**Offense books are team-specific** (155 books, mostly school names); **defense books are scheme
archetypes** (44 books: 3-2-6, 3-3-5, 3-4, 4-3, 4-2-5, multiple, + man/zone/shell/pressure variants).
Book slugs use the game's own separators (`&`, mixed `-`/`_`), and a handful need team aliases
(California→`cal`, Miami University→`miami_(oh)`, Texas A&M→`texas_a&m`, Southern Mississippi→`southern_miss`,
Middle Tennessee→`mid_tenn_state`, Sam Houston→`sam_houston_state`, Hawai'i→`hawaii`).

**Coach-row → slug map:** built at extract time by joining each HC's decoded playbook row to that team's
default-book slug, preferring teams that natively run their own book so a shared row resolves to the
book's home school. Baked into `manifest.json`. The app reads the user HC's Offensive/DefensivePlaybook
rows (via the coach-schema fix) and looks them up; unmapped rows fall back to the scheme archetype
(archetype enum → slug: OFF_AIR_RAID→air_raid, OFF_SPREAD→spread, DEF_MULTIPLE_DEFENSE→multiple, etc.).

## BCn decoding in TypeScript — PROVEN byte-exact (2026-08-31)

`src/main/textures/bcn.ts` decodes BC1, BC3 and BC7 (plain + sRGB) in pure TypeScript, replacing the python3+Pillow dependency in every extraction script. Why this is trustworthy:

- **BC7 is bit-exact by specification** — a correct decoder has no quality latitude, so equality against a reference implementation is provable, not aspirational.
- **The partition/anchor tables were recovered mechanically, never hand-typed.** Synthetic single-purpose blocks were fed to Pillow (a spec implementation): mode-1 blocks with black/white subsets and all-zero indices reveal the 2-subset partition row for each of the 64 partition ids; mode-2 blocks with black/red/green subsets reveal the 3-subset rows; setting every index bit to 1 makes anchor texels decode dimmer (they store one bit less), which reads the three anchor tables straight off the pixels. Recovered values match the known spec tables (P2 row 0 = 0xCCCC, anchor table leading 16×15).
- **BC1/BC3 interpolation was probed the same way**: floor division throughout ((2a+b)/3, (a+b)/2, /7 and /5 alpha ramps), BC1 3-color mode yields transparent black at index 3, and BC3's color half is 4-color regardless of endpoint order.
- **`node scripts/bc-check.ts` re-proves the whole decoder on demand**: ~200 real textures from this install (playcall diagrams BC7+sRGB, stadium field art BC1/BC3/BC7 incl. mip-chain top-slices) plus a seeded fuzz sweep with uniform coverage of all 8 BC7 block modes — every case byte-identical to Pillow (PASS 185/185 on first run; ~3.4M BC7 blocks, modes m0–m7 all exercised). A separate end-to-end check decoded 44 textures through the full new path (classify → decode → `png.ts` encode) and pixel-compared against the Pillow-era PNGs already shipped on this machine: 0 mismatches.

Supporting pieces: `src/main/textures/png.ts` (minimal zero-dependency PNG writer — RGBA8, filter 0, node zlib), `src/main/textures/resize.ts` (area-average downscale for portrait thumbnails; portraits are per-user output, not covered by the byte-exact promise since Pillow's thumbnail used Lanczos), `scripts/fb/texture.ts` (shared classify/decode/encode for all extractors). Python/Pillow survives ONLY inside bc-check.ts as the verification oracle.

This unblocks in-app extraction: the decoder lives under src/main and is electron-free, so first-run asset extraction from the user's own install (game folder known via Settings.gameDir) no longer has a native-tooling gap.

## Stack decision

**Electron, not Tauri.** The only maintained CFB 27 save parser is a Node.js library; Tauri would require bundling a Node sidecar, erasing its size advantage. Electron + electron-vite + React + TypeScript + Tailwind; better-sqlite3 snapshot history + diff engine → DynastyEvents; chokidar watcher (debounced, OneDrive-aware); electron-builder NSIS installer + auto-update.

### Playcall art & the per-play art question — SETTLED (2026-08-31)

The game's baked play art lives in `imageassetlibraries/ingame/playcall/` (122 textures, 512px BC7): **concept diagrams** (`pcc_*`: 42 pass, 21 run, 3 RPO, 10 defense shells, plus 9 counter-guides and 5 situational tiles), **play-type icons** (`pcpt_*`, 30), hot-route icons (`hri_*`, 12) and DL stunt cards (`psat_*`, 24). `scripts/extract-playcall-art.ts` pulls concepts+playtypes into `resources/game-icons/` and regenerates `src/shared/play-concepts.ts` — display names and grouping joined from the game's own `OffensivePlayConcepts`/`DefensivePlayConcepts` enums in Core-Schemas (all 72 members matched art; a small normVariants list resolves EA's own spelling drift between the two identifier sets, e.g. `Shot_Play`↔`shot`, `Man_Blitz`↔`blitz`). Shown as the Playbook tab's Concept Library.

**There is no baked per-play art.** The in-game play tiles are rendered at runtime from the same gamesheet geometry the app already extracts (alignments + route steps). And plays cannot be badged with concept art honestly: each play carries a type id (protobuf field 3 — the census over one book proves it's a play-type taxonomy: every value-14 play is an HB Draw, 195 = Inside Zone, 169 = Read Option, 205/207 = RPO Peek/Alert…) but that id space matches **neither** concept enum's values, no tuning-store table catalogs it, the playlibrary/global gamesheets carry no id→name table, and the pcc/pcpt EBX manifests hold only paths — the mapping lives in locked gameplay EBX. So per-play diagrams remain app-drawn from the book's own alignments/routes (`PlayArt.tsx`), which is the same mechanism the game itself uses.
